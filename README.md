# OpenSpec — 轻量版规格驱动开发

> 在开发前通过结构化流程定义需求、生成规格文档、拆分开发任务，让团队就"做什么"达成一致。

## 概述

OpenSpec 是一个轻量级的**规格驱动开发（Specification-Driven Development, SDD）** 工作流，专为 AI 辅助软件开发场景设计。它帮助你将模糊的需求想法，逐步转化为结构化的提案（Proposal）、详细的规格文档（Spec）、和可执行的任务清单（Tasks）。

## 适用场景

- 新功能开发前的需求梳理
- 技术方案评审与对齐
- 重构前明确目标和边界
- 团队协作时统一理解

## 不适用场景

- 已有详细 PRD，直接进入开发
- 已有完整代码实现，仅需测试执行
- 需要执行具体测试用例

## 核心工作流程

```
模糊需求 → Proposal（提案）→ Spec（规格）→ Tasks（任务）
                ↑____________确认___________↓
```

### 阶段一：Proposal（提案）

将模糊的需求想法转化为结构化的需求概述，澄清不确定性，识别关键假设。

- **输入**：口头描述、功能想法、草图
- **输出**：结构化提案文档
- **确认后进入**：Spec 阶段

### 阶段二：Spec（规格文档）

基于确认的 Proposal，生成详细的规格说明，包括功能拆解、API 设计、数据模型、业务流程和验收标准。

- **输入**：已确认的 Proposal
- **输出**：规格文档
- **确认后进入**：Tasks 阶段

### 阶段三：Tasks（任务拆分）

将 Spec 拆分为可执行的技术任务，标记依赖关系、优先级和工作量。

- **输入**：已确认的 Spec
- **输出**：任务清单
- **确认后**：可分配执行

### 阶段四：Review（评审）

分析现有 Spec/Proposal 的完整性、一致性、可执行性，识别潜在风险。

- **输入**：Spec/Proposal 文档
- **输出**：评审意见

## 使用方式

### 快速开始

| 场景 | 提示词 |
|------|--------|
| 开始新功能 | "帮我设计[功能名称]" |
| 继续 Spec | "基于[Proposal名称]生成Spec" |
| 继续 Tasks | "基于[Spec名称]生成Tasks" |
| 查看模板 | "请我读取references/[模板名]" |
| 查看示例 | "请我读取examples/demo_[阶段名]" |
| 评审方案 | "帮我看看这个方案有什么问题" |

### 核心原则

1. **迭代确认**：每个阶段必须确认后才进入下一阶段
2. **不过度设计**：保持精简，避免一开始就追求完美
3. **边界先行**：先识别边界条件和异常情况
4. **可执行性**：Task 必须足够具体，可直接分配执行
5. **简洁门禁**：如果描述比实现还复杂，说明过度设计了
